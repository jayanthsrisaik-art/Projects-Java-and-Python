# rankboard: a Kanban board whose card order survives concurrent drags

A small full-stack Kanban board: a **FastAPI + SQLite** backend and a **TypeScript** drag-and-drop UI.
The tutorial version stores an integer `position` per card. That works until the board is shared. This
project is about the part that version gets wrong: **storing and syncing order**.

* **Order keys you can always insert between.** Each card's `rank` is a base-62 fractional-index string
  (`a0`, `a0V`, `a1`, …). A move writes **one row**. A dense `position` column instead rewrites every
  card after the drop point (500 rows per op when prepending to a 1000-card column, measured below).
* **Appends stay short.** A key has a variable-length *integer part* that gets incremented on append, so
  1000 appends produce 3-character keys. A fraction-only scheme reaches 200 characters on the same
  workload.
* **Intent-based drops.** The client sends "after card X / before card Y" *as it saw the column*, not a
  number. The server resolves that against the current column inside one `BEGIN IMMEDIATE` transaction,
  with explicit fallbacks when X or Y has moved away. Two people dropping into the same gap both land
  between the anchors, in a deterministic order.
* **Rebalancing without lost edits.** Repeated inserts at one spot grow keys by about one character every
  6 inserts. Past a length limit (48 by default) the column is re-keyed in the same transaction. A
  rebalance does **not** bump card versions, so it never makes someone's concurrent title edit fail.
* **A change feed that never silently skips.** Every mutation appends to a per-board feed. Clients
  poll `GET /changes?since=cursor`, results are paged, and replaying a page twice is harmless. After the
  feed is compacted, a stale cursor gets **410 Gone** and the client reloads the snapshot. It does not
  quietly miss changes.
* **Optimistic UI that doesn't jump.** The TypeScript client runs a byte-identical port of the key
  algorithm and of the drop-resolution rules, so it predicts the server's rank. Both implementations are
  checked against shared vectors generated by the Python side (283 key cases and 53 placement cases).
* **Lost-update protection** for text edits and deletes (`If-Match` → 428/412 with the current card),
  plus client-chosen card ids, so a retried create is deduplicated instead of creating a second card.

## Architecture

```
web/ (TypeScript, no framework)                   rankboard/ (Python)
┌──────────────────────────────┐   JSON/HTTP   ┌───────────────────────────────────────┐
│ app.ts   DOM, drag & drop     │ ───────────▶ │ api.py    FastAPI routes, If-Match,     │
│ board.ts server state +       │              │           ETag, 410/412/428 mapping     │
│          optimistic overlay,  │ ◀─────────── │ store.py  SQLite: cards, change feed,   │
│          resolveDrop()        │  /changes    │           resolve_drop(), rebalance,    │
│ sync.ts  feed pager, 410 →    │  poll 1.5 s  │           compaction, invariants        │
│          snapshot reload      │              │ fracindex.py  key_between() etc.        │
│ fracindex.ts  (port)          │              │ bench.py  ordering-strategy benchmark   │
└──────────────────────────────┘              │ demo.py   two-user scripted session     │
        ▲ shared test vectors: samples/key_vectors.json (generated by vectors.py)        │
        └────────────────────────────────────────────────────────────────────────────────┘
```

Tables: `boards`, `columns`, `cards (UNIQUE(column_id, rank))`, `changes (seq AUTOINCREMENT, op, card JSON,
reason)`, `feed_floor` (highest compacted seq per board).

### Key format

`<integer part><fraction>` over `0-9A-Za-z`, which is in ASCII order, so Python `<`, JavaScript `<` and
SQLite's `BINARY` collation all agree. The integer part's first character encodes its length (`a`–`z` = 2–27
characters for non-negative integers, `Z`–`A` for negative ones). Appending increments the integer
(`a9` → `aA` → … → `az` → `b00`). Prepending decrements it (`a0` → `Zz`). Inserting between two keys with
the same integer part takes the midpoint of the fractions (`a0`,`a1` → `a0V`). Fractions never end in `0`,
so there is always room below. This is the scheme popularised by Figma's and rocicorp's
`fractional-indexing`, reimplemented here with one fix: decrementing to the reserved smallest integer
(`A000…0`) returns `A000…0V` instead of an invalid key.

### Drop resolution (`store.resolve_drop`, mirrored by `board.ts:resolveDrop`)

The moving card itself is ignored, then:

1. if `after_id` is still in the target column → immediately after it (before its *current* successor)
2. else if `before_id` is still in the target column → immediately before it
3. if no anchors were given → end of the column (`placement: "end"`)
4. if anchors were given but both are gone → end of the column (`placement: "fallback_end"`, and the UI
   tells the user)

## Usage

```bash
# run the app (UI at http://localhost:8000, API docs at /docs)
RANKBOARD_DB=rankboard.db uvicorn rankboard.api:create_app --factory --port 8000

python -m rankboard.demo            # scripted two-user session over HTTP (in-process)
python -m rankboard.demo --check    # ... compared against samples/scenario_expected.txt
python -m rankboard.bench           # ordering-strategy benchmark (deterministic)
python -m rankboard.vectors > samples/key_vectors.json   # regenerate shared TS/Python vectors
```

API summary:

| method & path | notes |
|---|---|
| `POST /api/boards` `{name, columns?}` | 201, returns snapshot |
| `GET /api/boards/{id}` | snapshot: board, columns, ordered cards, `seq` cursor (one consistent read) |
| `GET /api/boards/{id}/changes?since=&limit=` | `{changes, cursor, has_more}`; **410** if `since` was compacted |
| `POST /api/boards/{id}/cards` `{id?, column_id, title, after_id?, before_id?}` | 201 created, **200** replay of the same id, **409** id reused for a different card |
| `POST /api/cards/{id}/move` `{column_id, after_id?, before_id?}` | optional `If-Match`; response includes `placement` and `rebalanced` |
| `PATCH /api/cards/{id}` `{title?, description?}` | `If-Match` required: **428** missing, **412** stale (body has `current`) |
| `DELETE /api/cards/{id}` | `If-Match` required |

## Measured results: how to store card order

`python -m rankboard.bench` runs four deterministic single-column workloads through six strategies. It
counts rows written and final key size, records when float precision runs out, and checks that the stored
values sort in the intended order. Selected rows from `samples/bench_expected.md` (seed 7):

| workload | strategy | rows written / op | renumbers | max key chars (final) | order correct |
|---|---|---:|---:|---:|---|
| prepend ×1000 | dense integer index | 500.50 | 0 | int | yes |
| prepend ×1000 | rankboard keys | 1.00 | 0 | 3 | yes |
| append ×1000 | fraction-only keys | 1.00 | 0 | 200 | yes |
| append ×1000 | rankboard keys | 1.00 | 0 | 3 | yes |
| hotspot ×1000 | gapped integers (1024) | 46.13 | 90 | int | yes |
| hotspot ×1000 | float64 midpoint | 1.00 | 0 | 8 bytes | **NO** (precision lost at op 55) |
| hotspot ×1000 | rankboard keys (no rebalance) | 1.00 | 0 | 169 | yes |
| hotspot ×1000 | rankboard keys + rebalance@48 | 2.67 | 3 | 30 | yes |
| mixed ×2000 | dense integer index | 144.68 | 0 | int | yes |
| mixed ×2000 | gapped integers (1024) | 1.45 | 1 | int | yes |
| mixed ×2000 | rankboard keys + rebalance@48 | 1.00 | 0 | 4 | yes |

What the numbers show:

* Float midpoints lose precision after 55 inserts at one spot. After that, two cards get the same
  position, so their order is undefined.
* Gapped integers are fine for typical use, but at a hotspot they renumber the whole column every ~11
  inserts.
* Fractional keys need the integer part, or plain appends grow keys without bound. They also need a
  rebalance cap, or a hotspot grows keys by about one character every 6 inserts.

Workloads: `append` adds every card at the bottom. `prepend` adds every card at the top. `hotspot` always
inserts right below the first card (a triage pattern). `mixed` is 55% appends, 25% random inserts and 20%
random moves.

## Design decisions

* **The server computes ranks; clients only predict them.** Accepting ranks from clients would let two
  clients write the same key and would make the rebalance logic distributed. With intent-based drops,
  the server's transaction is the single place that orders a column.
* **One SQLite transaction per mutation (`BEGIN IMMEDIATE`).** The neighbour read, the rank write and the
  feed row are atomic, and writers are serialised. That is what makes the 8-thread test deterministic.
  `UNIQUE(column_id, rank)` is a backstop.
* **The rebalance keeps versions.** Rank is representation, not content. Bumping versions on a re-key
  would turn a background rebalance into spurious 412s for everyone editing that column.
* **Moves don't require `If-Match`, edits do.** A move expresses where the user wants the card relative
  to the cards they saw, so "last move wins" is the expected behaviour. A title edit based on a stale
  title is a lost update, so it is rejected. A move can still opt in to a version check.
* **The client ignores older versions from the feed.** A move's HTTP response can arrive before a poll
  that was generated earlier. Without the guard, the card would flicker back for one poll interval.
* **Polling instead of WebSockets.** A 1.5 s poll of an indexed range scan is simple and stateless, and
  works through any proxy. The feed contract (cursor, paging, 410) would carry over unchanged to SSE.

## Limitations

* Columns have a fixed order (`position`), and there is no column create/rename/reorder API. Card order
  is the subject here.
* There are no authentication, users or permissions. The `alice`/`bob` in the demo are just labels.
* One SQLite file serialises all writers. That is fine for a team board, but not for thousands of
  concurrent boards on one file.
* Compaction is a manual call (`Store.compact`). There is no background retention policy.
* A deleted card id is refused for reuse only while its delete is still in the feed. After compaction,
  a very late retry with that id would create the card again.
* The UI is deliberately minimal: drag-and-drop uses the HTML5 API (mouse only, no touch or keyboard
  reordering), and renaming uses `window.prompt`.
* The benchmark measures rows written and key sizes on a single in-memory column. It does not measure
  wall-clock database throughput.
