# deltasync — rsync-style binary delta sync, measured against chunk dedupe

When a large file changes slightly on one machine, sending the whole file again wastes
bandwidth. Comparing against the old copy at the *same offsets* stops working as soon as
anything is inserted or deleted, because every later byte shifts. **deltasync**
implements the rsync algorithm from scratch: the receiver sends compact block
signatures, the sender finds those blocks **at any byte offset** using an O(1) rolling
checksum, and only the unmatched bytes go over the wire. It also includes a FastCDC
content-defined chunker. Five transfer protocols are compared on synthetic edit
workloads, and every reconstruction is checked byte for byte.

Pure Python standard library. No services, no network, no downloads.

## Architecture

```
 receiver (has OLD)                          sender (has NEW)
 ───────────────────                         ────────────────
 make_signature(OLD) ──── DSSG bytes ─────▶  Signature.from_bytes
   per block: weak rollsum (4 B)               weak → [block ids] hash table
              + BLAKE2b-n strong (8 B)         slide window over NEW one byte at a time:
                                                 rolling a/b update in O(1)
                                                 weak hit → confirm with strong hash
                                                 prefer block after previous match
 apply_delta(OLD, delta) ◀── DSDL bytes ────   emit COPY(offset,len) / LITERAL(bytes)
   bounds-check every COPY                     (adjacent COPYs coalesced)
   rebuild + verify BLAKE2b-256 of NEW
   temp file → fsync → atomic rename
   on hash mismatch: retry with 32-byte strong hashes, then whole file
```

| module | role |
|---|---|
| `rollsum.py` | rsync weak checksum `a = Σx`, `b = Σ(L−i)x` (mod 2¹⁶); O(1) `roll` and `shrink` |
| `signature.py` | block signatures, rsync-style block size heuristic (√n, multiple of 8, 700 B … 128 KiB), `DSSG` wire format |
| `delta.py` | rolling-match delta generation, `DSDL` wire format with strict decoder (magic, version, truncation, unknown tags, trailing bytes) |
| `patch.py` | in-memory and streaming (`seek`-based) apply with range checks and whole-file hash verification |
| `sync.py` | end-to-end local sync through the real wire bytes; atomic replace, permission bits kept, collision retry |
| `cdc.py` | fixed chunking and FastCDC (Gear hash, normalized chunking, high-bit masks) |
| `bench.py` | synthetic workloads + five protocols with byte accounting in both directions |
| `cli.py` | `signature`, `delta`, `patch`, `sync`, `inspect`, `chunks`, `bench` |

## Usage

```bash
# three-step protocol (as two machines would run it)
python -m deltasync signature samples/basis.csv basis.sig --block-size 256
python -m deltasync delta basis.sig samples/target.csv change.delta
python -m deltasync patch samples/basis.csv change.delta rebuilt.csv   # verified, atomic
python -m deltasync inspect change.delta

# one-shot local sync (prints a JSON report; --dry-run leaves DST untouched)
python -m deltasync sync samples/target.csv copy_of_basis.csv --block-size 256

# fixed vs content-defined chunk reuse between two versions
python -m deltasync chunks samples/log_v1.bin samples/log_v2.bin --avg 4096

# full benchmark (≈3 s) → results/bench.md, results/bench.json
python -m deltasync bench --out-dir results
```

### Sample inputs and expected outputs

`samples/basis.csv` → `samples/target.csv` changes the header, inserts a row near the
top, moves 60 rows to the end, edits one price and appends 40 rows (generated by
`samples/make_samples.py`). Expected outputs are in `samples/expected/`, and
`tests/test_sync_cli.py` checks the CLI against them exactly:

* `basis_to_target.delta`: the exact delta bytes (generation is deterministic).
* `inspect.txt`: 9 ops. 12,032 of 14,057 bytes are copied from the basis, including the
  moved rows (`COPY basis[4608:5632]` near the end). The whole delta is 2,100 bytes.
* `sync_dry_run.json`: 634 B signature + 2,100 B delta = **2,734 wire bytes for a
  14,057 B file**.
* `chunks.json`: after a 34-byte prefix insert and a 1 KB delete in a 64 KiB file,
  fixed 4 KiB chunks reuse **0%** of the bytes and FastCDC reuses **78.7%**.

## Results (measured, `results/bench.md`)

The files are 256 KiB of synthetic log/CSV-like text with occasional binary blobs, and
each row is the mean over 3 seeds. The numbers are total wire bytes in both directions,
so lower is better. All 120 reconstructions were byte-identical.

| workload | whole-file | aligned-blocks | fixed-dedupe | cdc-dedupe | rsync-delta |
|---|---:|---:|---:|---:|---:|
| identical | 262,144 | 1,160 | 1,024 | **917** | 4,557 |
| append-4k | 266,240 | 5,258 | **5,140** | 9,303 | 9,000 |
| prepend-1b | 262,145 | 263,306 | 263,317 | 10,821 | **4,560** |
| insert-1k-middle | 263,168 | 133,940 | 135,936 | 23,917 | **6,291** |
| scattered-20-edits | 262,144 | 41,437 | 134,892 | 162,316 | **18,735** |
| delete-10k | 251,904 | 103,555 | 105,508 | 10,306 | **5,294** |
| move-32k-section | 262,144 | 185,480 | 50,200 | 56,150 | **6,686** |
| full-rewrite | **262,144** | 263,304 | 263,296 | 263,183 | 266,700 |

What the numbers show:

* **Shifts break offset-based methods.** A single prepended byte makes aligned blocks
  and fixed chunks resend roughly the whole file. rsync sends 4.6 KB, mostly the
  signature, and FastCDC sends 10.8 KB.
* **rsync wins on localized edits**: insert, delete, move and scattered edits. Its
  matching granularity is 700 B blocks, against CDC's ~8 KiB chunks. With 20 scattered
  edits, each CDC chunk that is touched is resent whole (162 KB). rsync sends 18.7 KB.
* **rsync loses when nothing moved.** For an unchanged file its 12-byte-per-700-B
  signature (4.5 KB) costs more than chunk hash lists (~1 KB). On `append-4k` the short
  final basis block no longer sits at the end of the target, so it can't match (the
  same behaviour as rsync) and is sent literally. Aligned blocks and fixed chunks win
  that case.
* **Unrelated content**: every method is slightly worse than just sending the file.
  rsync's overhead is 4.5 KB of signature.
* **Block size trade-off** (scattered edits): 128 B → 27.5 KB, 512 B → **16.8 KB**,
  700 B (default) → 18.7 KB, 8 KiB → 134 KB. Smaller blocks shrink the delta but grow
  the signature, and the √n heuristic lands close to the optimum.

Timing (pure Python, 256 KiB): about 0.03 s per rsync sync and 0.04 s per FastCDC pass
on this container. These are only for comparing methods with each other.

## Design decisions

* **The two-level checksum follows rsync.** The weak sum is cheap and rolls in O(1),
  so it can be tested at every offset. Only weak hits pay for BLAKE2b. False weak hits
  are counted in `DeltaStats`.
* **End-to-end verification over trust.** Each delta carries the BLAKE2b-256 of the
  target, and `patch` refuses mismatched output. This catches strong-hash collisions
  (the tests force one with 1-byte strong hashes) and a basis that changed in
  between. `sync` then retries with 32-byte strong hashes and falls back to the whole
  file, the same recovery rsync uses.
* **Matches prefer continuity.** When several basis blocks share a checksum, which is
  common in repetitive data, the block right after the previous match is chosen.
  Adjacent COPYs merge, so an unchanged run becomes a single op.
* **Every count comes from wire bytes.** `sync` and the benchmark serialize and parse
  the signature and delta, so the byte counts and the parsers are exercised for real.
* **Strict decoders.** Bad magic, an unknown version, truncation, overlong varints,
  zero-length ops, unknown tags and trailing bytes are all rejected. Copies outside
  the basis are rejected before any output is written.
* **Atomic writes.** Output goes to a temp file in the destination directory and is
  fsynced, then renamed over the destination. A failed patch leaves no partial file.
* **The baselines are complete protocols**, each counted in both directions:
  aligned-blocks sends per-block hashes up and changed blocks down; the dedupe methods
  send chunk hashes up, plus the recipe and missing chunk bodies down.

## Tests

`python -m pytest -q` runs 41 tests:

* the rolling checksum against direct computation at every offset, and when shrinking
* varint edge cases
* 300 randomized round trips: inserts, deletes, substitutions, moves and duplications,
  on low-entropy alphabets that cause many weak collisions
* tail-block semantics, moved and duplicated blocks, and forced weak and strong
  collisions
* wrong-basis and corrupted-delta rejection
* FastCDC tiling, bounds, determinism and shift resistance
* atomic sync, no-op, dry-run and collision retry
* exact CLI output against `samples/expected`
* a small benchmark that checks every method's reconstruction

## Limitations

* Single files only: no directory trees, metadata beyond permission bits, deletions
  or rename detection.
* Both ends run in one process. The wire formats are real, but there is no network
  transport or pipelining.
* Literals are not compressed. rsync `-z` would shrink the literal bytes in the text
  workloads considerably.
* The whole file is held in memory for delta generation (patching can stream).
  Measured pure-Python throughput here is about 4–10 MB/s, so this is not meant for multi-GB files.
* The strong-hash length is fixed (8 bytes by default) rather than sized to file
  length the way rsync does. Whole-file verification plus retry covers correctness,
  but very large files would deserve a longer default.
* The benchmark data is synthetic. Real-world savings depend on how edits are
  distributed in your files.
